# Disabled-first deployment and recovery

This kit contains reconstruction specifications. All tenant actions and licensing decisions remain Pending. No importable flow package exists. An authorized administrator executes these steps in the named test tenant and records [evidence](evidence-template.md). Use synthetic customer codes and harmless PDFs. Do not send messages to real customers.

## Build and enable sequence

1. Record all entry gates and administrators in the evidence template. Confirm the exact tenant/environment/site before provisioning. A missing gate blocks its dependent component.
2. Follow [SharePoint provisioning](../sharepoint/provisioning-guide.md) and [schema](../contracts/sharepoint-schema.json). Enable specified unique/indexed columns and version history. Verify one account per role. Direct Orders edits must fail for staff. Verify snapshots are immutable for staff and automation never overwrites deterministic names. Approvers/Production can read their required snapshot/released files. Views do not replace permissions.
3. Create private environment configuration from [example](../config/environment.example.json), outside tracked files. Record GUIDs and actual connections in protected operational storage. No passwords/tokens enter JSON, logs or commits. Keep EnableAutomation=false and EnableNotifications=false. Fix SLA=72/24 and DispatcherBatchSize=25 for pilot. Require AllowedRoles keys and configured UPNs lowercase/trimmed with no duplicate normalized identities; verify the automation account has only the approved service role.
4. If licensed, create solution CopilotProcessKit, environment variables for each configuration setting and connection references for SharePoint, Standard approvals, Outlook and Teams. Bind flows to the dedicated identity. AllowedRoles and LibraryPaths can be JSON text environment variables parsed to objects. Keep IDs/UPNs as explicit approved values. Actual managed/unmanaged exports may be produced only from the tenant later; record exact file/hash/version without claiming the documents are an export.
5. If solutions/Dataverse ALM is unavailable, build four individual disabled flows. Add identical named `Config` Compose objects and approved native connections to each flow. Record every value/version and owner in a protected checklist. Changes require manual edits to all four disabled flows and a diff review. This path has no equivalent automated connection rebinding, solution transport or managed upgrade/rollback guarantee.
6. Reconstruct [F01](../flows/F01-dispatcher.md), [F02](../flows/F02-approval-worker.md), [F03](../flows/F03-notification-worker.md) and [F04](../flows/F04-watchdog.md) in disabled state. Preserve action names, timeouts, retry policies and concurrency. Recreate scope expansions as documented; save actual designer action inventory. Check every required command against [action map](../flows/action-map.csv).
7. Run binding probes in an isolated test list/job/file with flows disabled. Capture Author Email/Editor Email, normalized Choice output, file identity/version/ETag/size, list entity type and actual REST ETag path. Execute conditional MERGE once with a current ETag and once with a stale ETag; prove stale request gives 412 with no mutation. Validate documented Copy file (deprecated), operation CopyFile, accepts Destination File Path and Overwrite Flag=false and rejects existing targets without mutation. Modern Copy file only exposes Destination Folder; do not assume it can rename. If deprecated CopyFile is unavailable, block activation until Owner approves a tested native SharePoint REST CopyTo replacement with overwrite=false, updates the action map, and re-runs copy recovery cases. A missing probe blocks activation.
8. Verify dummy approval creation/ID persistence/wait response bindings under explicitly authorized internal test identities. Prove response UPN/time/outcome are genuine connector outputs and no default success path exists. This probe can send approval notifications; record the actual Create action notification option. Disable F02 during dispatcher-only tests. EnableNotifications controls F03 only.
9. Save disabled drafts and record their actual versions/action inventory. Set EnableAutomation=true in the approved test configuration; enable F01 with F02/F03/F04 disabled. Exercise Submit, missing consent/artwork, authorization, stale revision and deterministic file paths. Keep notifications false. A Validate may create New jobs, so inspect them before enabling F02.
10. Enable F02 for approved internal test assignees, then F04. Exercise approvals, queue races, timeout/recovery and 24h reminder with real elapsed time or a separately documented synthetic deadline fixture in the isolated test tenant. Never backdate real decisions. Run all applicable [acceptance cases](acceptance-cases.csv). Record actual fixture changes and restore them; do not call fixtures proof of a real 72h wait.
11. After role/state/idempotency gates pass, set test-only recipients/channel, EnableNotifications=true, and enable F03. Confirm actual received messages, uncertain-send recovery and backlog behavior. Inspect active runs when changing flags because a run already past its gate may continue.
12. Build/authenticate/evaluate the agent and report components with their respective guides. Publish to pilot Teams users only after source permission, unsupported question and prompt-injection cases pass. Reconcile reports and training competency before expansion.
13. Review all evidence, failures and remaining Pending cases. Record Owner approval of pilot scope, retention and known limits. Expansion requires no unexplained failed safety case and actual tenant evidence. Local validation alone never clears this gate.

## Repair a partial transition

Pause F01 and F02 if approval/file effects may race; disable F03 for delivery incidents. Inspect active runs and leave long waits recorded; a disabled trigger does not cancel a run already waiting. Take a versioned redacted incident record with actual command/order/job/event/outbox IDs and file metadata. Do not click Resubmit on a failed flow run.

For a command, prove automation wrote the recovery receipt after authorization from command version history and Editor. Ignore incoming human PayloadJson. Compare Orders.LastCommandKey, Status, Revision and every Plan field. If the mutation already applied, recreate only missing deterministic effects and compare existing immutable payloads, then mark Applied. If the old order is intact, inventory snapshot/released files and approval cards before resetting Pending. A conflicting file, missing receipt identity, unknown approval card or different LastCommandKey remains NeedsReview. Do not alter business state to hide incomplete effects. Repair writes use the approved service/admin operator and conditional ETags; record actual before/after versions.

For a Creating job, inspect actual approval center/run outputs. If Create might have succeeded, never reset New automatically. Recover the real unique ApprovalId and wait on that existing ID through a reviewed recovery flow. If identity cannot be established, preserve NeedsReview and block production. For expiry/decision ordering, accept a timely response only if the current order is still AwaitingApproval with matching key/revision. Once expiry applied, old decisions cannot revive it; Owner documents a supported resubmission/new approval cycle or separately authorized incident remediation.

For Sending/uncertain outbox, inspect Sent Items/channel. Record delivered/not-delivered/uncertain. Mark Sent only with observed evidence; reset Pending only after conclusive nondelivery and documented Owner retry approval. Retain NeedsReview if uncertain. A notification failure never rolls Orders back. Source NeedsReview views and flow run history remain the fallback if incident notifications also fail.

## Pause and rollback rehearsal

1. Record reason, UTC time, active flow run IDs, current config and actual saved flow versions. Set both flags false. Disable F01–F04 triggers; inspect and explicitly handle active runs before any reconfiguration. Do not assume disabling cancels an approval wait or card.
2. Preserve all commands, receipts, events, jobs, outbox entries, immutable snapshots and released files. Export/audit tenant state only through an authorized method. Do not delete lists, reset revisions, restore an old list over newer records or overwrite artwork.
3. Rebind the previously verified disabled flow versions and configuration through actual tenant version history/export if available. Manual fallback requires rebuilding from the saved inventory and comparing actions; no fabricated restore artifact exists. Restore approved knowledge/report versions separately with recorded hashes and source permissions.
4. Inspect LastCommandKey/receipts, New/Creating/Waiting jobs, stale approvals and Sending messages. Cancel obsolete approval cards manually where supported. Reconcile partial writes before releasing same-order barriers. Quarantine unused snapshots through an audited procedure; retain history.
5. Re-run authorization, stale revision, duplicate claim, current key/revision/time decision, file identity and uncertain-send cases in the isolated test scope. Re-enable F01 first, then F02/F04, and F03 last after test delivery evidence. Record exact versions, operator and go/no-go decision. Unresolved uncertainty keeps the affected order blocked.

## Limits that remain
