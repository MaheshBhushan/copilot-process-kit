# SharePoint pilot provisioning

Owner: Owner/admin · Version: 1.0 · Tenant execution: Pending

Use an authorized development site with synthetic records and internal test accounts. Follow the [schema](../contracts/sharepoint-schema.json), [process contract](../contracts/process.json), [permission matrix](permissions-matrix.csv) and [configuration example](../config/environment.example.json). JSON describes construction; it is not an import package. No tenant has been provisioned by this kit.

## Prerequisites and configuration

1. Owner names an administrator, backup administrator and dedicated licensed automation account. Confirm SharePoint, Exchange, Teams, Power Automate and Approvals entitlements, approved DLP grouping, data region and retention. Confirm Copilot Studio and Power BI licensing separately. Record the actual decisions before enabling flows.
2. Create or select the test site. Keep public/external sharing disabled for this pilot. Use separate groups Print Sales, Print Prepress, Print Approver, Print Production and Print Owner. Keep administrator membership separate from the business Owner role. Owner has business authority to Cancel; the role does not automatically grant site administration.
3. Copy environment.example.json to a protected private file outside the committed kit. If stored in a working tree, add that exact private filename to the local ignore rules before populating it. Replace every `.invalid` identity/site and `REPLACE-` value. Do not store passwords or tokens. Use lower-case exact UPN keys in AllowedRoles, with arrays of the contract role names. Include AutomationUPN with Automation and each authorized approver with Approver. Verify every mapped identity against actual internal accounts.
4. Record real site path, environment ID, list GUIDs, TeamId and ChannelId. LibraryPaths must be server-relative paths for the actual same site. Keep EnableAutomation and EnableNotifications false. Verify 72/24-hour constants and batch size 25. Deployment must reject all placeholder values and identities ending `.invalid` before enablement.

## Create lists and columns

1. Use Site contents > New > List > Blank list. Create Orders, OrderCommands, ApprovalJobs, OrderEvents and Outbox with those exact names. Enable version history for each list.
2. Preserve the built-in Title column. Create each custom field using the exact ASCII `internalName` first. You may rename the display label later. Check the field settings URL or actual connector metadata to verify the internal name. Creating a friendly name first can produce an encoded internal name that breaks expressions.
3. For every field in the schema, choose its `type`, `required`, `default`, `choices`, `indexed` and `unique` values. Text means Single line of text; Note means Multiple lines of plain text; Number means numeric; DateTime means Date and Time. Currency uses EUR and two decimals. Disable fill-in choices. Number fields with `integer: true` use zero decimal places; flow validation also rejects fractional values. Do not create lookup columns. OrderKey text joins all records.
4. A null default means no default. A nullable field remains blank until the appropriate transition. Date-only fields are unsuitable for deadlines. Keep the site timezone documented; connector and report verification must confirm UTC storage and conversion.
5. Enforce unique values and indexes on Orders.OrderKey, OrderCommands.RequestKey, ApprovalJobs.ApprovalKey, OrderEvents.EventKey and Outbox.MessageKey. Create all other declared indexes before loading data. Keep these constraints active during recovery.
6. Use the exact contract choices. Required SharePoint fields are unconditional; command-specific inputs remain nullable in OrderCommands and the dispatcher checks them against the command's requiredInputs. This allows Submit before QuoteEUR exists and Complete without irrelevant Submit fields. No human should write PayloadJson. Forms show the separate Title, CustomerCode, ProductType, Quantity, QuoteEUR, DueAt, ApproverUPN, ProductionUPN, DraftFilePath, CustomerConsentRef, QCReference, WasteQuantity, Reason and PreflightChecklistRef fields as appropriate.
7. Hide ProcessingState, processing timestamps, AppliedRevision, ErrorCode, ErrorDetail and automation response fields from staff forms for usability. Hiding columns does not secure them. A caller can supply initial output values when adding an item. Dispatcher polls Pending only, derives authority from immutable Created By, validates all inputs and disregards service output values as evidence. Forged Automation commands must fail the immutable author check even if PayloadJson names a service account.
8. Build the views in schema.views. Filter active views explicitly; use indexed status/time/key fields. Expose ReleasedFilePath in ProductionQueue, never a draft link. Views improve navigation and do not enforce security. Configure bounded flow pagination for pilot scale and verify actual result counts before growth.

Microsoft documents the [column types and options](https://support.microsoft.com/en-us/sharepoint/lists/data-and-lists/list-and-library-column-types-and-options) and [index setup](https://support.microsoft.com/en-gb/sharepoint/data-and-lists/add-an-index-to-a-list-or-library-column?nochrome=true).

## Create libraries

1. Use Site contents > New > Document library. Create DraftArtwork, ProductionFiles and ProcessKnowledge. Enable version history. Create ApprovalSnapshots inside ProductionFiles. Record exact library paths in private configuration.
2. DraftArtwork accepts synthetic PDFs for this pilot. Prepress edits; Sales contributes where needed; automation reads. Validate rejects missing files, external URLs, traversal (`..`), other extensions and files larger than 20 MB. Prepress still checks print suitability manually.
3. ProductionFiles grants staff Read only. Automation creates snapshots and releases without overwriting deterministic paths. Use `ApprovalSnapshots/{ApprovalKey}.pdf` and `{ApprovalKey}-approved.pdf`. For ApprovalKey `PO-000123-r2`, the released name stays `PO-000123-r2-approved.pdf` even after business Revision advances. Nobody uses the mutable draft as a released file. Library history supports investigation but does not make administrator edits impossible.
4. ProcessKnowledge contains only Owner-approved published guides. Follow the knowledge publishing guide when Markdown is unsupported by the grounding surface. Use supported files or actual SharePoint pages and verify source readiness. Store a restricted admin-only negative-test document in a separate uniquely secured library or folder outside the shared knowledge folder.

## Apply permissions

SharePoint grants permissions at securable object scopes. This design uses unique list/library permissions and command creation instead of relying on hidden columns. Review Microsoft's [permission guidance](https://learn.microsoft.com/en-us/sharepoint/understanding-permission-levels) and [list/library customization procedure](https://support.microsoft.com/en-us/sharepoint/lists/sharepoint-sharing-and-permissions/customize-permissions-for-a-sharepoint-list-or-library).

1. In each list/library settings page, open permissions and stop inheriting. Remove inherited Members/Edit and any broad sharing grants. Keep explicit administrators and the automation identity. Audit group membership, direct grants and sharing links because grants are additive. Do not delete unrelated site groups.
2. Create `PrintCommandSubmit` by copying Read and adding Add Items. Keep the dependencies selected by SharePoint. Exclude Edit Items, Delete Items, Delete Versions, Manage Lists, Manage Permissions and Override List Behaviors. Grant this level on OrderCommands to Sales, Prepress, Production and Owner. Approvers only respond through Approvals and need no human command grant. Where item-level settings are available, restrict staff reading to their own commands. Automation must read all commands; give its controlled account the rights required to bypass the read-own limitation and verify with actual tests. Restrict elevated permissions to this list.
3. Grant staff Read on Orders. Only automation and administrators can create/edit Orders. ApprovalJobs, OrderEvents and Outbox need no staff access; administrators and automation can inspect them. Grant the automation account an Add-and-Read level on OrderEvents, with no Edit/Delete. Its usage is append-only. Do not assign it a broader overlapping grant that defeats this restriction.
4. Give automation Add-and-Read on ProductionFiles; no Edit/Delete or overwrite permission. If the connector action requires extra permissions, stop and verify the minimal scoped grant with harmless files before enabling Release. Record any exception explicitly. The flow must still disable overwrite and reconcile an existing destination. Staff only read snapshots and released files; Production follows ReleasedFilePath after ReadyForProduction.
5. Apply the matrix to DraftArtwork and ProcessKnowledge. Only Owner and administrators edit approved process knowledge. Restrict sharing to owners and review links after provisioning. Manage Approvals independently; list access does not assign decision rights.
6. Test through the browser and connector with each ordinary role account, not an administrator session. Direct Orders edit, command edit/delete, snapshots overwrite and forged Automation submission must fail. A direct link must not bypass the restricted knowledge test. Keep outcomes Pending until observed and retain redacted account, object, command and flow evidence.
